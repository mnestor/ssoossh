# Running several agents in parallel

Multiple agents can develop separate features of ssoossh at the same time, each
in its own git worktree on its own branch, merging into `main` when done. This
document defines how, and the constraints that make it safe.

The danger is not merge conflicts. Conflicts are loud and you fix them. The
danger is the things in this repo that **merge cleanly and are wrong
afterwards**: generated files that no longer match their source, a schema
whose two driver migrations have drifted apart, and host state that two runs
quietly share. Git's merge is textual. It does not know `docs/openapi.yaml`
is derived from Go annotations, and it does not know that a line-numbered
reference stops meaning anything the moment another branch inserts a line
above it.

That last point applies to this document as much as to any code. It once
carried five `Makefile#L<n>` links; by the time anyone checked, every one of
them was wrong, one by 263 lines. References here name targets and functions
now, because those survive an edit and a line number does not.

## The rules, in short

1. One worktree per feature. Never two agents in one checkout.
2. Schema is single-owner. Only one branch at a time touches `server/model/` or
   `server/resources/migrations/`.
3. Nobody runs `make test-e2e` except the integrator. It is serialised by an
   flock now, so a stray second run waits rather than corrupting the first —
   but it still changes host state, so it is not a background task.
4. Never hand-resolve a generated file. Take one side, then regenerate.
5. Merge one branch at a time, rebasing each on the new `main` before its turn.
6. Run the post-merge ritual after every branch lands, not once at the end.
7. Verify every agent report against the tree before acting on it. An agent's
   summary is a claim, not evidence.

## Setup

Each feature gets a worktree, branched off `main`, using the repo's `feat/`,
`fix/`, `chore/` prefixes:

```sh
make worktree NAME=<feature>            # branch chore/<feature>, off main
make worktree NAME=<feature> BASE=main WORKTREE_BRANCH=feat/<feature>
```

Worktrees share one `.git` object store but have independent checkouts and
indexes, so two agents cannot see or clobber each other's files. Claude Code
drives this natively: the `Agent` tool accepts `isolation: "worktree"`, and
`/EnterWorktree` moves an interactive session into one.

`make worktree` exists because doing it by hand trips over the same three
things every time, and only the first is obvious:

1. `/workspace` is root-owned, so `git worktree add ../ssoossh-<feature>`
   fails with "could not create leading directories". The script makes and
   chowns the directory first.
2. **A failed `git worktree add -b <branch>` still creates the branch**, so
   the obvious retry fails differently — "a branch named ... already exists"
   — and reads like a stale worktree rather than the previous command's
   half-completed work. The script reuses an existing branch.
3. A fresh worktree has no `server/frontend/dist/index.html`, and about
   fifteen `server/bootstrap` tests fail on "failed to read index.html"
   until one exists. The script runs the frontend build.

If you do create one by hand, verify with `git worktree list` afterwards.

**Never let two agents share a checkout, including the main one.** This is
rule 1 and it is easy to break by accident when worktree creation fails and
the convenient fallback is to give every agent the same directory with its
own `git switch -c`. That does not isolate anything: branch `HEAD` is a
property of the checkout, not of the agent, so all of them end up on
whichever branch switched last, writing into one tree. The first agent to
commit sweeps up everyone else's half-finished work onto its branch. The
failure is silent while it happens and only visible afterwards in a diff
nobody can attribute.

Before creating worktrees, commit or stash anything untracked on `main`.
Untracked files do not propagate into a new worktree, so an agent that starts
from a dirty `main` will plan against documents it cannot see.

Tear down when merged:

```sh
git worktree remove ../ssoossh-<feature>
```

## Ownership

Two resources cannot be held by more than one branch at a time. Assign them
before starting, and record the assignment somewhere the agents can read.

| Resource | Why it is single-owner |
| --- | --- |
| `server/model/` and `server/resources/migrations/` | One migration file per driver, edited by hand, must stay consistent across both |
| `make test-e2e` | Uses a fixed host account and a real `sshd`; not isolated by worktrees |

Everything else can be worked in parallel. Prefer assigning whole files or whole
packages to a branch rather than splitting a file between two.

## The three hazards

### 1. Checked-in generated files

These are tracked in git and produced by a generator:

| File | Generated by | Source of truth |
| --- | --- | --- |
| [openapi.yaml](../openapi.yaml) | `make openapi` | swag annotations in `server/controller`, `server/webtypes`, `internal/apitypes`, `server/model` |
| `frontend/src/lib/api/generated/{apitypes,enums,webtypes}.ts` | `make types` | Go structs listed in [tygo.yaml](../../tygo.yaml) |
| `go.sum` | `go mod tidy` | `go.mod` |
| `frontend/pnpm-lock.yaml` | `pnpm install` | `frontend/package.json` |

Two branches that both touch wire types will both regenerate, and the outputs
collide. Resolve by taking either side wholesale and re-running the generator.
Editing generated output by hand produces a file that matches neither branch and
that CI rejects.

CI does catch it. `make openapi-check` and `make types-check` hash the output
either side of a regeneration run rather than asking git, so a stale merge
fails whether or not the file was committed. See
[wire-types.md](../wire-types.md).

### 2. One migration file per driver

The schema lives in exactly two tracked files, which are duplicates of each
other in different dialects:

```
server/resources/migrations/postgres/20260101000000_init.up.sql
server/resources/migrations/sqlite/20260101000000_init.up.sql
```

GORM's `AutoMigrate` is deliberately not used. As
[server/model/model.go](../server/model/model.go) states, a field added to a
model must also be added to both migration files by hand. So a schema change is
a three-file edit that has to stay mutually consistent, and two branches making
schema changes edit the same regions of the same files.

Hence rule 2: exactly one branch at a time owns schema. If a second feature
needs a column, it either waits for the first to land and rebases, or the two
schema changes are made together on the owning branch up front.

### 3. `make test-e2e` touches the host, and is serialised for you

Worktrees isolate the filesystem. They do not isolate the host.

The end-to-end suite (`make test-e2e`, [e2e-testing-plan.md](e2e-testing-plan.md))
reaches outside its worktree in four ways:

| Shared thing | Where |
| --- | --- |
| The `ssoossh-e2e` local account, created and unlocked via sudo | `test/e2e/harness/sshd.go` |
| `sshd` run as root via sudo | `test/e2e/harness/sshd.go` |
| PAM service files under `/etc/pam.d` | `test/e2e/harness/pam.go` |
| Container and listener ports | `harness.StartNATS`, `freePort` |

**`make test-e2e` now takes an flock** (`/tmp/ssoossh-e2e.lock`), so a second
run waits rather than interfering. "One run at a time" used to be a rule in
this document; it is now enforced by the target. `make test-e2e-unlocked`
skips the lock if you deliberately want a parallel run. CI is unaffected
either way — `e2e.yaml` invokes `gotestsum` on `./test/e2e/...` directly and
never goes through the make target, and each job has the host to itself.

That lock matters because the failure it prevents was silent, not loud. The
PAM service files used to be named by fixed constants, and the stanza in one
names *that run's* server URL and CA file — so a second run overwrote the
first, pointed the first run's authentication at the second run's server, and
whichever finished first deleted the file out from under the other. The names
now carry a pid and a counter. The NATS ports were likewise hardcoded
(42421–42435, hand-picked to be distinct from each other, which held within a
run and not at all across two); they are allocated now.

`docker-compose.yml` still binds fixed host ports (`127.0.0.1:8888:8888`), so
only one compose stack can run at a time. That one is not serialised for you.

## What does parallelize safely

`make test`, `make lint`, `make cover`, `make verify`, `make semgrep`, and the
frontend build all write only inside their own worktree. `server/frontend/dist`
is gitignored and rebuilt per worktree, which is why it is a prerequisite of
the Go targets: the Go side embeds it and will not compile without it — and it
now has the frontend sources as prerequisites, so it rebuilds when they change
rather than only when it is missing. Running these concurrently in several
worktrees is fine.

`make semgrep` is on that list only recently. It used to bind-mount the
working directory, which resolves on the HOST docker daemon — so from any
worktree other than the one the devcontainer was started in, the mount came up
empty and the scan died with "Invalid scanning root: frontend/src". It ships
the sources in with `docker cp` now (`scripts/semgrep.sh`) and reproduces CI's
scope exactly: same image, same rule packs, same 50 files.

## Verifying agent reports

Agent summaries describe the plan the agent formed, which is not always the
diff it produced. Both failure directions have been observed here, in the same
round:

- Reporting a gate that was never run, or run partially. "All tests pass"
  after running one package. "Lint is clean" against a stale
  `golangci-lint` cache.
- Reporting a feature in confident, specific detail — which mechanism, what
  reads from it, why that design was chosen — that is absent from the code.
  One branch described wiring `host_mappings` in `signreply.go`, including
  its rationale for populating it as output rather than input, and had
  written none of it.

Neither is deliberate, and neither is caught by reading the summary more
carefully. Check the tree instead. Per branch, before it merges:

```sh
git -C <worktree> status --porcelain     # anything uncommitted is not landing
git -C <worktree> log --oneline main..HEAD
git -C <worktree> diff main...HEAD --stat
cd <worktree> && go build ./... && golangci-lint run ./... && make test
```

Then check the specific claims:

- **Uncommitted work.** Three agents in one round reported a green gate and
  exited with the work still in the working tree. In a container whose
  worktrees sit on overlay, that work dies with the next rebuild.
- **The named artifact exists.** If the report says it wired a table, added an
  endpoint, or created a seam, grep for it. A one-line `grep -rn` settles it.
- **The test proves what it claims.** A passing test is not evidence on its
  own. For a test written to catch a specific defect, reintroduce the defect
  and confirm the test fails, then restore. That is the only way to know a
  regression test regresses. Applied to the request-binding guard, this turned
  "29 tests pass" into the discovery that all 29 passed with the guard
  removed.
- **Coverage exclusions still match.** Line-range regexes silently stop
  matching after a merge shifts lines. See hazard 2.

None of this is expensive; it is minutes per branch against hours of
untangling. Treat a report's claims as the list of things to check, and take
an honest "I did not get to this" at face value — it is more useful than a
confident inaccuracy, and worth saying so in the dispatch brief.

## Merge order

Serialize. Do not merge several branches at once.

1. The schema-owning branch lands first, so everyone else rebases onto the final
   column set rather than guessing at it.
2. Each remaining branch, in turn: rebase onto the updated `main`, resolve, run
   the post-merge ritual on the branch, then merge.
3. Rebase rather than merge. Generated-file conflicts then surface once per
   branch instead of compounding across a tangle of merge commits.

## Post-merge ritual

Run after **each** branch lands, not once at the end. Step 1 repairs the
silent-breakage hazard; step 2 is the gate.

```sh
make openapi && make types   # 1. regenerate, never hand-merge; commit the result
go mod tidy                  #    if go.mod/go.sum conflicted
pnpm install --lockfile-only #    (in frontend/) if pnpm-lock.yaml conflicted
make lint && make test       # 2. full gate
```

Then, once, after the final branch has landed:

```sh
make test-e2e
```

Step 1 is the one most easily skipped and the one whose omission is hardest to
notice later: a stale generated file fails CI on a branch that did not write it.

## Known escape hatches

One change would remove most of the remaining friction above. It is not done,
and is worth doing before running many features in parallel becomes routine:

- **Split the init migration into additive timestamped files.** golang-migrate
  is already the driver ([server/bootstrap/db.go](../server/bootstrap/db.go)),
  so branches could each add their own migration instead of editing a shared
  one. Note that two branches picking the same timestamp prefix would still
  collide, so timestamps must be taken at creation time.

## Devcontainer gotchas that look like your bug

These are environment, not repo, and each one produces a failure that reads
as a problem with the code you just wrote:

| Symptom | Cause and fix |
| --- | --- |
| `pnpm test` says `Cannot find package 'vitest'`, or `pnpm check` reports ~23 bogus `toBeInTheDocument` errors | The container relocates every `node_modules` to `/node_modules/<mangled-path>` and symlinks it back, which breaks pnpm's peer resolution. Make it a real directory again: `rm frontend/node_modules && mv /node_modules/_workspace_frontend frontend/node_modules`. Do not "fix" it with `preserveSymlinks`. |
| `pnpm install` or `go build ./...` fails on permissions | `/workspace/.pnpm-store` and `/go/pkg/mod` are owned by another uid. `sudo chown -R "$(id -un):$(id -gn)"` them. |
| `git commit` hangs forever | `commit.gpgsign=true` with a dead agent socket. Use `--no-gpg-sign`, and **start** a rebase with `--no-gpg-sign` too — the sequencer records the signing option in `rebase-merge/gpg_sign_opt` and re-reads it on every `--continue`, so setting the config afterwards does not help. |
| `docker build`/`pull` fails with `error getting credentials - exit status 255` | `~/.docker/config.json` names a VS Code credential helper that only works inside VS Code. Use a clean config: `DOCKER_CONFIG=$(mktemp -d)`. `scripts/semgrep.sh` already does this for you. |
| `undefined: pkcs11.*` from anything Go | `CGO_ENABLED=1` is required for every Go command here. The Makefile sets it; a bare `go test ./...` does not. |
