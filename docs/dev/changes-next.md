## Database schema

A dedicated schema audit on 2026-08-22
([database-schema-audit-2026-08-22.md](database-schema-audit-2026-08-22.md))
went deeper than the general audit and **corrected two of its claims** — see
the corrections note at the end of this section. Its one live bug is in
[changes-now.md](changes-now.md); the rest is below, in that audit's own
suggested order.

### First: decide the retention story

Findings 3 and 4 are one decision, not two — the foreign-key question cannot
be answered without it.

- **Nothing is ever deleted.** There is no `DELETE` against any application
  table anywhere in the codebase and no retention job. Every table grows
  without bound: one `certificate_requests` row per login attempt, one
  `certificates` row per issuance, forever. Compounding it, `ListForIdentity`
  fetches a user's complete certificate history with no `LIMIT` and no
  pagination (`server/service/certificate.go:51-57`).
- **The audit table's FK conflicts with ever pruning.**
  `certificate_request_decisions.certificate_request_id` is a `NOT NULL` FK
  onto `certificate_requests`. The decisions table is documented as permanent
  and append-only; `certificate_requests` is what needs retention. Pruning a
  request will either be blocked by the FK or, if someone reaches for
  `ON DELETE CASCADE` to unblock it, will **silently delete the audit record
  that was meant to outlive it.**
- **No `ON DELETE`/`ON UPDATE` is declared on any of the four foreign keys**,
  so both dialects default to `NO ACTION`. The intended behavior on user
  deletion has never been decided.

The decisions needed: retention policy per table; and either the decisions
table drops its FK and keeps a plain copied ID (consistent with how it
already handles decider identity — copied values, deliberately no `user_id`
FK), or `certificate_requests` is declared permanent too.

| 7 | Write the paired `.down.sql` migrations. | `.claude/rules/database.md` opens with "Always include rollback instructions" — this is a direct violation of the project's own rule, invisible so far because there has only ever been one migration. The startup path already reasons about downgrades (`ALLOW_DOWNGRADE`), a rollback story that cannot currently be executed. Do it while the answer is a trivial set of `DROP TABLE`s. |
| 8 | Add `certificate_request_id` to `certificates`. | There is no join between `certificate_request → decision` and `certificate → user`, so nothing can answer "which approval produced this certificate". Concrete failure mode today: `SignedReplyHandler` deliberately treats a missing owner as non-fatal, writing `user_id = NULL` — with no request ID either, that row is **permanently orphaned**, dropping out of `ListForIdentity` with nothing able to reattach it. |
| 9 | Add `CHECK` constraints on the enums and the type/nullable-column pairings. | Neither dialect file contains a single `CHECK`. A typo in a status string produces a row no guarded `WHERE status = ?` will ever match again, invisible to the sweep. A partial check like `CHECK (type = 'host' OR user_id IS NOT NULL)` turns a silent disappearance into a loud failure at the bad write. |
| 10 | Fix index coverage to match actual query shapes. | Make `idx_certificate_requests_status` into `(status, created_at)` to cover the sweep's range; make `idx_certificates_user_id` into `(user_id, issued_at DESC)` to cover `ListForIdentity`'s sort. Missing entirely: `certificate_requests.user_id`, `enrollments.user_id`, and `certificate_request_decisions.decided_at`. |
| 11 | `UNIQUE` on `certificates.serial_number`. | Serials are the key a KRL revokes by. A collision at 2^63 is vanishingly unlikely, which is exactly why the constraint costs nothing — it converts an astronomically rare "revoking one certificate silently revokes an unrelated second one" into a failed insert. |
| 12 | Test asserting parity between the two dialect files. | They are in exact parity today, and nothing keeps them that way. `db_test.go` covers the migration *runner* thoroughly (22 tests) but never compares the two schemas to each other. |
| 13 | Cursor-based pagination on `ListForIdentity`. | Shape already settled: `?after=<uuid>`, ordered `created_at DESC, id DESC` — **not** offset, which breaks under concurrent issuance. Needs the `(user_id, issued_at DESC)` index from #10 anyway. Pair with the retention decision above. |
| 14 | Resolve the unused `enrollments` table. **Defer until service enrollment resumes.** | `approveServiceEnrollment` does not create an `Enrollment` row; it writes a UUID into `certificate_requests.enrollment_token`, while `EnrollmentService.Retrieve` is a stub returning "not implemented". So live enrollment state is a denormalized token carrying none of what `model.Enrollment` was designed to hold — no `expires_at`, no `redeemed_at`, no `option_set` snapshot, no `UNIQUE` on the token. Either the enrollment path starts writing the table it was designed around, or the table is dropped and `certificate_requests` becomes the documented home. Leaving both is how they drift further apart. |

`host_mappings` is likewise unreferenced, but that one is straightforwardly
"designed, not built" rather than a disagreement.

### Corrections to the 2026-08-21 audit

Both were re-verified; do not carry the originals forward.

- **"SQLite silently allows orphans" is wrong.**
  `addSqliteDefaultParameters` unconditionally appends `foreign_keys(1)` to
  every connection string and rejects any attempt to override it
  (`server/bootstrap/db_pocketid.go:127-128,140`). SQLite enforces the
  constraints too; the two dialects behave the same. The real finding is
  narrower: the intended deletion behavior was never decided.
- **"`certificate_requests` are hard-deleted" is wrong.** They are never
  deleted — they accumulate (see the retention section above).

## Features with existing design documents

Sequenced. The ordering below is the recommendation, not an arbitrary list.

### 1. Admin and auditor roles — the critical path

Design: [features.md](../features.md)'s admin section, which is
thorough — OIDC-group-based, two narrow roles, no DB role column,
session-scoped revocation window.

**Re-verified**: zero implementation. No `Role` or `IsAdmin` field on
`model.User`, no admin controller, no admin middleware, and
`server/controller/users.go` explicitly documents "deliberately no route to
list or read other users."

Start here. It blocks the runtime-editable half of certificate lifetime
policy *and* the effective-config view, so it is genuinely on the critical
path rather than a parallel nice-to-have.

Open questions to resolve first:

- Is session TTL an acceptable de facto admin-revocation window, or does
  admin need a shorter session or step-up re-auth?
- Where does the effective-config view redact? CA key and client secret are
  obvious. Trusted-proxy ranges and subnet policy are judgment calls.

### 2. Certificate lifetime and source-network policy

Design: [certificate-lifetime-policy.md](../certificate-lifetime-policy.md).
Unusually complete — longest-prefix subnet matching, host-rule-wins-outright,
narrowing-only invariant, config schema drafted. Zero code.

Splits cleanly in two, and the split matters: **step 1, the config-file-only
policy engine, has no blocker and can ship independently of admin roles.**
Only the runtime-editable host-rules half waits on §1 above.

**Known defect, identified 2026-08-23: `source-address` pinning is welded to
the lifetime rule.** `pin_source_address` lives on `SourcePolicyEntry`, so
"how long may this certificate live" and "from which addresses may it be
used" share one rule list, one longest-prefix match, and a tie-break decided
by duration. Refining the lifetime map silently rewrites the pinning map. On
top of that, what gets granted is the observed source IP as a bare `/32`, not
the rule's configured CIDR, which is what both the config comment and the
design document describe. This is a rework of the config surface and the
evaluation split, not a patch. Full write-up, including the pin-only config
that yields zero-length enrollments and the missing `service enroll` source
addresses, in
[certificate-lifetime-policy.md](../certificate-lifetime-policy.md) under
"Known defect: `source-address` is welded to the lifetime rule".

Open questions:

- Is the certificate acceptable on the wire in the multi-instance wake
  message once it crosses the network between instances? (An mTLS/NATS
  authorization question, not a new exposure.)
- Is service-account linkage evaluated at enrollment time or retrieve time?
  Retrieve is more truthful about where the certificate is actually used, but
  it silently re-tiers an unattended job with no human present to see why.

### 3. Multi-instance safety

Design: [multi-instance-safety-plan.md](multi-instance-safety-plan.md). Zero
code, but the central bug is identified precisely — `Wait` discards the wake
message's certificate payload and falls through to a 410 — with a small,
scoped fix already described.

Independent of NATS. This can be built and tested today against two
`CertRequestService` instances sharing gochannel; it does not need the signer
split.

Open question: how does "multi-instance mode" get declared — inferred from
NATS being configured, or an explicit setting?

### 4. Host certificate issuance — completed

Host certificate first issuance is now implemented and complete. The client CLI
is complete (`host sign/renew/sync/principals`), `HostService.Renew` and
`HostService.SyncPrincipals` exist for authenticated renewal and principal
syncing, and `certtypepolicy.go` now routes `CertificateTypeHost` through
`flowSigning` like user and PAM certificates, with authorization gated on the
SSH server admin role.

The implementation includes:

- Real approval flow via `CertRequestService.Approve` (not a separate
  `HostService.Sign`, which was a misunderstanding in the design notes)
- Authorization check gating issuance on `middleware.SSHServerAdminChecker`
  before request binding to prevent claiming requests
- Principal derivation from the request's hostname (validated against the regex
  pattern in `internal/crypto/ssh`)
- Empty `host_mappings` table (output-only: written by signreply after signing,
  consumed by `host sync` — not validated as input since the approver vouches
  for the hostname and allowlisting would duplicate
  `cert_options.host.require_group`)

The `host` subcommand's `--help` text describes functionality that is now
implemented and working.

### 5. Service certificate enrollment — two gaps

Mostly built: client commands, `EnrollmentService.Retrieve`,
`EnrollmentController`, `flow: flowEnrollment` in the policy table, and
narrowed options persisted at approve time all exist.

Two things are missing:

- **Account linkage.** `service.Identity.ServiceAccounts` exists, but the
  create-request flow has no field recording *which* service account a
  `service enroll` call is for. This is a schema gap, not just a policy one.
- The `enrollments` table question in the table above (#4).

## Not designed at all

Raised in [dev/changes-next.md](changes-next.md)
and elsewhere, with no design work behind them yet. Each needs a design pass
before it is schedulable.

- Admin host-enrollment flow.
- Per-host certificate policy settings.
- Ownership reassignment for service and host certificates when the owning
  user leaves or is disabled, so automation keeps working after they are gone.
- Console-login PAM module (code-based, no browser or network needed on the
  console itself). Mentioned as a future direction only.
- Client-side TLS pinning. Only `insecure_skip_verify` exists today.
- LDAP enrichment. `LDAPConfig` exists with URL, bind DN, and base DN fields,
  explicitly marked `// TODO: not yet consumed by service.AuthService` in
  `server/config/types.go`. No LDAP client code anywhere in the tree.
