## What this proposes

A host resolves a username to its uid, primary gid, all group memberships,
home and shell from ssoosshd over HTTPS, with nothing provisioned per host.
Ephemeral hosts boot from an image and have a working directory; long-lived
hosts keep a persistent cache and stop beating on the server.

It is the NSS counterpart to `pam_ssoossh`: PAM answers "may this person
act", NSS answers "what POSIX identity is this name". Login authorization
stays with SSH certificates. Nothing here issues or validates one.

Server side it is behind `nss.enabled`, defaults off, and requires
`ldap.enabled`: every POSIX identity, people and shared or service accounts
alike, is a directory entry with a uid attribute (decided 2026-10-17). The
host side never needs the certificate pipeline.

## Threat model

The asset is the name to uid mapping. An attacker who can make a host
believe `alice -> uid 0`, or `alice -> bob's uid`, owns the host. In
priority order:

1. Code loaded into setuid processes (`sudo`, `su`, `passwd`, `sshd`). With
   userdb that code is systemd's `nss-systemd`, not ours. Our exposure there
   is the content of the records we serve, which `nss-systemd` validates
   and copies.
2. A lying or compromised endpoint: edge proxy, load balancer, app tier. TLS
   protects the wire, not the server.
3. Replay of a captured response (mitigated by TLS alone, as with sssd).
4. Availability: a slow or dead directory wedging logins, `sudo`, `ls -l`,
   and boot. With userdb the caller's timeout is systemd's 45 s, not ours
   (U4), so the daemon must always answer fast.
5. Local users abusing the world-writable userdb socket: forcing upstream
   traffic, or impersonating `sshd` to force synchronous refreshes.
   Impersonation is closed by R5 and refresh floods by R6. Cold misses for
   made-up names are accepted as they are with sssd (R33): the concurrency
   cap bounds the host, the server's per-key miss alert is the signal, and
   no per-uid budget is built unless an operator asks.
6. Environment overrides in setuid callers (U9). `nss-systemd` reads
   `SYSTEMD_BYPASS_USERDB` and `SYSTEMD_ONLY_USERDB` with plain `getenv`
   (`src/shared/userdb.c:670-688`), so a local user can hide this service
   from a setuid program they start. The result is fail-closed (user
   unknown, fewer groups) except for rules that **deny** by directory
   group, such as sudoers `!%group`. Do not use directory groups in deny
   rules. `SYSTEMD_NSS_SERVER_SIDE_NSS=1` (U13) instead routes the
   caller's lookups through `systemd-userdbd`, so the peer the daemon sees
   is `systemd-userwork`, not sshd: the sshd freshness refresh (R5) is
   skipped and the entry ages out at the normal TTL. Fail-safe.
7. Directory data shaped into passwd fields. `gecos` is rendered from a
   template over directory attributes (R35); a `:` or a newline in it
   would corrupt `getent` output and anything that parses it. The server
   sanitises the rendered value before storing it, and `nss-systemd`
   mangles anything that still fails `valid_gecos()`
   (`src/shared/user-record.c:265-293`), so the worst case is a mangled
   display name, never a broken record. Names are validated with the same
   rules `nss-systemd` applies before it calls any service (R23).
8. A uid or gid moved in the directory. Files on every host belong to the
   number, not the name: a changed `uidNumber` orphans everything the
   person owns, and a reused one hands it to whoever gets the number next.
   sssd follows the directory. This design does not (R38): a stored uid or
   primary gid never changes on sync, a differing directory value is held
   as a pending change with a daily alert until an admin accepts it, and a
   tombstoned uid stays reserved for `tombstone_retention`.
9. Two entries with one name. `getpwnam` returns one record, so a second
   claimant to a login name is either a directory mistake or an attempt to
   receive someone's logins. Neither entry is served while it lasts (R39),
   the same fail-closed rule as a shared uid.

Every lookup requires a fleet API key, so exposure is that of LDAP with a
shared bind account (the usual sssd deployment), not anonymous bind. Any
host holding a key can ask for any name; that is accepted. Out of scope:
per-host identity (mTLS, host certificates). The key is baked into the
image, never provisioned per host, and is readable by root only.

## Architecture

Split by process, as sssd does, but the module loaded into callers is
systemd's rather than ours:

```
 caller (sudo, sshd, ls)                        host                      server
 +----------------------+   varlink, AF_UNIX  +----------------+  HTTPS  +-----------+
 | glibc -> nss-systemd | ------------------> | ssoosshd-nss   | ------> | ssoosshd  |
 | systemd's module,    | /run/systemd/userdb/| Go, root       | pinned  | /api/nss/*|
 | not ours             | com.github.mnestor. | cache, policy  | + key   | Part 1    |
 +----------------------+ ssoossh             | Part 3         |         +-----------+
                                              +----------------+
```

- `nss-systemd` is shipped by systemd and already loaded on most hosts. It
  queries every socket in `/run/systemd/userdb/` in parallel and turns
  JSON user and group records into `struct passwd` / `struct group`. We
  write no code that runs inside callers.
- `ssoosshd-nss` implements systemd's `io.systemd.UserDatabase` varlink
  interface and does everything else: pinned HTTPS with the fleet key, the
  cache, host-side options. One process to audit.

### Alternatives considered (2026-10-11)

| Option | Why not |
| --- | --- |
| HTTP inside the NSS module (`gate-sso/nss_gate`, Google OS Login) | The fleet key would have to be readable by every process that resolves a user. No trusted cross-process cache (unprivileged callers cannot write one), so no offline mode. Network calls from sandboxed callers (`RestrictAddressFamilies=AF_UNIX`, `PrivateNetwork=`, SELinux `nsswitch_domain`) and during early boot. OS Login gets away with it because its server is link-local plain HTTP with no secret on the host, and it still ships a cache module and refresh timer. `nss_gate` itself disables TLS verification and has memory-safety bugs. |
| Own C module plus Go daemon (the 2026-10-10 draft) | C in every setuid caller, a private socket protocol to version, a second repo, a zig-built `.so`. Userdb removes all of it; its costs are U3 to U7. |
| sssd `id_provider = proxy` loading an HTTP module | The proxy provider calls the module synchronously inside `sssd_be`'s event loop (`src/providers/proxy/proxy_id.c`), so one slow fetch stalls the backend. No refresh on login, so sudo-group removal waits for sync plus cache TTL. sssd on every Debian/Ubuntu host. |
| sssd straight at the source LDAP | Zero ssoossh code, and right for hosts that can reach LDAP. This proposal exists for hosts that cannot, and for shell self-service. |
| nscd protocol listener | The only route that serves musl (musl queries `/var/run/nscd/socket` after `/etc/passwd`, `src/passwd/nscd_query.c`). Unsafe on glibc, which asks nscd before `nsswitch.conf` and trusts its "not found". Deferred until a musl host needs directory users (U2). |

## Transport trust

Responses are plain JSON over HTTPS. No response signing: sssd, nslcd, OS
Login and hosted directories all trust TLS plus a credential. The earlier
JWS/JWKS layer was dropped on 2026-10-10.

The daemon's one trust root is its TLS pin, configured like
`ldap_tls_cacert` / `ldap_tls_reqcert = demand`: `tls_ca_file` (a private CA
bundle) or `tls_spki_pin` (SHA-256 of the server's SubjectPublicKeyInfo),
baked into the image. The system bundle is not used; proxy and certificate
environment variables are ignored. TLS 1.3 only, matching `ssoossh-pam`.

## PAM: keep `pam_ssoossh` standalone

Do not route the PAM module through the NSS daemon. The module already has
most of what the split would buy and is packaged for musl, FreeBSD and macOS
where a Linux-only daemon would not exist. Two small changes inside the
module, as independent PRs ahead of this work:

- `proxy=` argument defaulting to `CURLOPT_PROXY ""`.
- `tls-ca-file=` wired to `CURLOPT_CAINFO`, optionally `tls-pin=` to
  `CURLOPT_PINNEDPUBLICKEY`.

Stale notes to clear while there: `src/pam_ssoossh.c:62` says console
endpoints do not exist (they do: `POST /api/certs/console`), and the README
lists console mode as unverified against a real server.

## Decisions

Taken 2026-10-09 and 2026-10-10:

- ~~Module language: C.~~ Superseded 2026-10-11: no module (U1).
- ~~POSIX fields: separate `user_posix` table; `users` unchanged.~~
  Superseded 2026-10-17: `posix_users`, unique on uid and anchored on the
  directory entry; `users` is still unchanged (R22).
- Reverse lookup by uid (`/user/uid/:uid`): kept, unrestricted; the key is
  the control.
- SOC may revoke NSS keys and read their logs; not create or rotate.
- Cache timeouts: `entry_cache_timeout` 90 min; `entry_negative_timeout`
  15 s; `cache_expire_offline` never. sssd defaults throughout.
- `/api/ca`: unchanged.
- Service enrollment codes: left as is.
- PAM hardening PRs ship first; SELinux ships as `ssoossh-nss-selinux`,
  built from this repo (2026-10-10).
- ~~Packaging (2026-10-10): one `ssoosshd-nss` package carries the daemon
  and `libnss_ssoossh.so.2`, the module built here with `zig cc`.~~
  Superseded 2026-10-11: the package carries the daemon and its systemd
  units only (U1).
- Daemon placement: `ssoosshd-nss` is its own binary (`cmd/ssoosshd-nss`,
  Linux-only) in `mnestor/ssoossh`, sharing `internal/` packages; never a
  subcommand of the `ssoossh` client. ~~`mnestor/ssoossh-nss` is C-only.~~
  No `mnestor/ssoossh-nss` repo (U1).
- No server-side group gate, global or per key. Narrowing is host config.
- Response signing: none.
- Routes: path parameters (`/user/name/:name`, `/user/uid/:uid`,
  `/group/name/:name`, `/group/gid/:gid`), not query strings. Kept
  explicit even though all-numeric names are now rejected (R17), so the
  original disambiguation reason no longer applies; see README R17.
- Names: all-numeric user and group names are rejected (2026-10-10). Still
  true under the relaxed rules adopted 2026-10-17 (R23).
- Daemon source: new top-level `/nssd` (2026-10-10).
- Rate limiting: per `(key_id, source IP)` with the connection's IP, never a
  header; per-key miss rate alerts, never blocks.
- Key headers: `X-Ssoossh-Key-Id` and `X-Ssoossh-Key-Secret`; the id is
  fixed for the key's life; rotation replaces only the secret.
- Key ownership: optional `description` and an assigned `group` per key;
  `admin.nss_key_group` creates keys and assigns groups.
- User self-service: shell only, by name from `nss.allowed_shells`, sent as
  `shell_pref` beside the LDAP `shell`.

Taken 2026-10-11:

- Host interface: systemd userdb. `ssoosshd-nss` implements
  `io.systemd.UserDatabase` on
  `/run/systemd/userdb/com.github.mnestor.ssoossh`; stock `nss-systemd`
  is the glibc side; the module part was removed (U1).
- Platform floor: systemd 245+, glibc, `systemd` on the `passwd:` and
  `group:` lines. RHEL 8 (systemd 239, maintenance ends 2029-05-31) and
  musl are out of scope (U2).
- Service name `com.github.mnestor.ssoossh`, reverse-DNS as the userdb API
  recommends, matching the client's Windows policy key namespace.
- Socket activation: systemd owns the listening socket so lookups queue
  across daemon restarts.
- Disabled and deleted users: `locked: true` plus `disabled_shell` (U6).

Taken 2026-10-17:

- LDAP is required: `nss.enabled` with `ldap.enabled: false` is a startup
  error. No OIDC claim source for POSIX attributes (R36).
- POSIX rows anchor on the directory entry: `posix_users` unique on `uid`,
  carrying `directory_id` and `dn`, with a nullable `user_id` that the
  login path sets through the existing LDAP resolution (R22). Shared and
  service accounts are rows with no `user_id`. `users.subject` is opaque
  to NSS and is never read as a uid (R37).
- Status is derived, never stored as its own state machine: `deleted_at`,
  then `users.disabled_at` of the linked person (any source), then the
  directory's own disabled flag (R24).
- Names are stored verbatim and matched byte for byte on both sides. The
  R17 regex is replaced by the relaxed rules `nss-systemd` itself applies,
  plus a 32-byte cap; the server no longer lower-cases and the daemon's
  `case_sensitive` option is gone (R23).
- Attribute names are configurable (`nss.attributes`), and `gecos` is a
  Go template over an allow-listed set of attributes, sanitised after
  rendering (R35).
- Two entries with one uid: neither is served while the collision lasts,
  with a daily audit alert (R29). Fail closed.
- uid and primary gid are frozen at first sight. The sync never changes
  them; a differing directory value becomes a pending change that an
  admin accepts explicitly, and a tombstoned uid stays reserved until
  retention ends (R38). Name, home, shell and gecos follow the directory.
- Names are unique among users and among groups, enforced by the schema
  and by the sync: two live entries with one name are both withheld with a
  daily alert, and a tombstone keeps its name until retention or an admin
  purges it (R39).
- The `privileged` record section goes only to uid 0 peers (R27).
- Per-instance limiter, negative cache and usage counters are accepted;
  the usage flush is an additive upsert (R28).
- Cold-miss floods from local users are accepted as with sssd (R33).

Taken 2026-10-18:

- Directory reads: full sync of the `nss.user_filter` and
  `nss.group_filter` scope, as proposed. Considered and declined:
  on-demand reads only (a group's member list would hold only the members
  the server happened to know), and on-demand reads that fetch a found
  group's full member list one level deep (complete lists, but a second
  kind of row whose own groups are unread). With full sync the filter is
  the control over what the server stores.
