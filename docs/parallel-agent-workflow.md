# Running several agents in parallel

Multiple agents can develop separate features of ssoossh at the same time, each
in its own git worktree on its own branch, merging into `main` when done. This
document defines how, and the constraints that make it safe.

The danger is not merge conflicts. Conflicts are loud and you fix them. The
danger is the three things in this repo that **merge cleanly and are wrong
afterwards**: generated files that no longer match their source, coverage
exclusions whose line numbers have shifted, and a schema whose two driver
migrations have drifted apart. Git's merge is textual. It does not know
`docs/openapi.yaml` is derived from Go annotations, and it does not know that
`keypair\.go:133\.10,136\.4` stops meaning anything the moment another branch
inserts a line above 133.

## The rules, in short

1. One worktree per feature. Never two agents in one checkout.
2. Schema is single-owner. Only one branch at a time touches `server/model/` or
   `server/resources/migrations/`.
3. Coverage exclusions are single-owner per Go file.
4. Nobody runs `make test-e2e` except the integrator, and only serially.
5. Never hand-resolve a generated file. Take one side, then regenerate.
6. Merge one branch at a time, rebasing each on the new `main` before its turn.
7. Run the post-merge ritual after every branch lands, not once at the end.

## Setup

Each feature gets a worktree, branched off `main`, using the repo's `feat/`,
`fix/`, `chore/` prefixes:

```sh
git worktree add ../ssoossh-<feature> -b feat/<feature>
```

Worktrees share one `.git` object store but have independent checkouts and
indexes, so two agents cannot see or clobber each other's files. Claude Code
drives this natively: the `Agent` tool accepts `isolation: "worktree"`, and
`/EnterWorktree` moves an interactive session into one.

Before creating worktrees, commit or stash anything untracked on `main`.
Untracked files do not propagate into a new worktree, so an agent that starts
from a dirty `main` will plan against documents it cannot see.

Tear down when merged:

```sh
git worktree remove ../ssoossh-<feature>
```

## Ownership

Three resources cannot be held by more than one branch at a time. Assign them
before starting, and record the assignment somewhere the agents can read.

| Resource | Why it is single-owner |
| --- | --- |
| `server/model/` and `server/resources/migrations/` | One migration file per driver, edited by hand, must stay consistent across both |
| `exclude-from-coverage.txt` entries for a given `.go` file | Entries are line ranges; another branch editing the same file invalidates them silently |
| `make test-e2e` | Uses a fixed host account and a real `sshd`; not isolated by worktrees |

Everything else can be worked in parallel. Prefer assigning whole files or whole
packages to a branch rather than splitting a file between two.

## The four hazards

### 1. Checked-in generated files

These are tracked in git and produced by a generator:

| File | Generated by | Source of truth |
| --- | --- | --- |
| [openapi.yaml](openapi.yaml) | `make openapi` ([Makefile:98](../Makefile#L98)) | swag annotations in `server/controller`, `server/webtypes`, `internal/apitypes`, `server/model` |
| `frontend/src/lib/api/generated/{apitypes,enums,webtypes}.ts` | `make types` ([Makefile:120](../Makefile#L120)) | Go structs listed in [tygo.yaml](../tygo.yaml) |
| `go.sum` | `go mod tidy` | `go.mod` |
| `frontend/pnpm-lock.yaml` | `pnpm install` | `frontend/package.json` |

Two branches that both touch wire types will both regenerate, and the outputs
collide. Resolve by taking either side wholesale and re-running the generator.
Editing generated output by hand produces a file that matches neither branch and
that CI rejects.

CI does catch it. `make openapi-check` ([Makefile:104](../Makefile#L104)) and
`make types-check` ([Makefile:131](../Makefile#L131)) hash the output either
side of a regeneration run rather than asking git, so a stale merge fails
whether or not the file was committed. See [wire-types.md](wire-types.md).

### 2. `exclude-from-coverage.txt`

Per [.claude/rules/test-go.md](../.claude/rules/test-go.md), code that cannot be
tested gets its exact uncovered line ranges added to
[exclude-from-coverage.txt](../exclude-from-coverage.txt). The entries are
regexes carrying line and column positions:

```
server/service/certrequest\.go:485\.87,487\.4
```

They are applied by a plain grep against the coverprofile
([Makefile:187](../Makefile#L187)):

```
grep -v -E -f exclude-from-coverage.txt .coverage/coverage-all.out > .coverage/coverage.out
```

`server/service/certrequest.go` alone has 17 such entries. If branch A inserts
lines above one of those ranges and branch B edits that entry, the merge
succeeds and every one of A's shifted ranges now matches nothing. There is no
conflict marker and no error at merge time. The exclusion has simply stopped
excluding, and coverage numbers move for reasons unrelated to any test.

Two mitigations, both required:

- One branch owns the exclusions for a given `.go` file.
- The integrator re-derives ranges with `make cover` after each merge, rather
  than trusting the merged text.

### 3. One migration file per driver

The schema lives in exactly two tracked files, which are duplicates of each
other in different dialects:

```
server/resources/migrations/postgres/20260101000000_init.up.sql
server/resources/migrations/sqlite/20260101000000_init.up.sql
```

GORM's `AutoMigrate` is deliberately not used. As
[server/model/model.go](../server/model/model.go) states, a field added to a
model must also be added to both migration files by hand. So a schema change is
a three-file edit that has to stay mutually consistent, and two branches making
schema changes edit the same regions of the same files.

Hence rule 2: exactly one branch at a time owns schema. If a second feature
needs a column, it either waits for the first to land and rebases, or the two
schema changes are made together on the owning branch up front.

### 4. `make test-e2e` is not parallel-safe

Worktrees isolate the filesystem. They do not isolate the host.

The end-to-end suite ([Makefile:182](../Makefile#L182),
[e2e-testing-plan.md](e2e-testing-plan.md)) creates and unlocks a local account
with a fixed name, `ssoossh-e2e`, and runs `sshd` as root via sudo. See
`test/e2e/README.md`. `docker-compose.yml` likewise binds fixed host ports
(`127.0.0.1:8888:8888`).

Two agents running `make test-e2e` at the same time will fight over one account
and one `sshd`, and the failures will look like flakes rather than contention.
E2E is run by the integrator, on the merged branch, one run at a time.

## What does parallelize safely

`make test`, `make lint`, `make cover`, and the frontend build all write only
inside their own worktree. `server/frontend/dist` is gitignored and rebuilt per
worktree, which is why it is a prerequisite of the Go targets: the Go side
embeds it and will not compile without it. Running these concurrently in
several worktrees is fine.

## Central wire-up points

Features that add a route or a service will conflict here, because each one
appends to the same list. These conflicts are mechanical: keep both sides.

| File | What collides |
| --- | --- |
| [server/bootstrap/router.go](../server/bootstrap/router.go) | Route registration in `initRouter` |
| [server/bootstrap/bootstrap.go](../server/bootstrap/bootstrap.go) | Service construction |
| [server/model/model.go](../server/model/model.go) | Model list (already single-owner) |

## Merge order

Serialize. Do not merge several branches at once.

1. The schema-owning branch lands first, so everyone else rebases onto the final
   column set rather than guessing at it.
2. Each remaining branch, in turn: rebase onto the updated `main`, resolve, run
   the post-merge ritual on the branch, then merge.
3. Rebase rather than merge. Generated-file conflicts then surface once per
   branch instead of compounding across a tangle of merge commits.

## Post-merge ritual

Run after **each** branch lands, not once at the end. Steps 1 through 3 repair
the three silent-breakage hazards; step 4 is the gate.

```sh
make openapi && make types   # 1. regenerate, never hand-merge; commit the result
go mod tidy                  #    if go.mod/go.sum conflicted
pnpm install --lockfile-only #    (in frontend/) if pnpm-lock.yaml conflicted
make cover                   # 2. re-derive coverage exclusion line ranges
make lint && make test       # 3. full gate
```

Then, once, after the final branch has landed:

```sh
make test-e2e
```

Step 2 is the one most easily skipped and the one whose omission is hardest to
notice later. If `make cover` reports coverage for lines that are supposed to be
excluded, the ranges have shifted and the entries need rewriting against the
merged file.

## Known escape hatches

Two changes would remove most of the friction above. Neither is done, and both
are worth doing before running many features in parallel becomes routine:

- **Split the init migration into additive timestamped files.** golang-migrate
  is already the driver ([server/bootstrap/db.go](../server/bootstrap/db.go)),
  so branches could each add their own migration instead of editing a shared
  one. Note that two branches picking the same timestamp prefix would still
  collide, so timestamps must be taken at creation time.
- **Make coverage exclusions position-independent.** Function-scoped or
  marker-based exclusions would survive line shifts, removing hazard 2 and the
  recurring "update coverage exclusion line ranges" commits it causes.
